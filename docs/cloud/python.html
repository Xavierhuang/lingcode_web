Python on LingCode Cloud

TL;DR: Python runs on LingCode Cloud in two tiers. Python custom functions — short-lived per-request work in a firejail sandbox, stdlib-only, with a single network hole to the backend gateway — are live in Preview today and this doc's function section applies. Python app hosting (FastAPI/uvicorn / long-running Docker containers) is designed and code-shipped but the runtime is not yet stood up on prod — deploys currently queue and never swap in (the runner throws caddy_admin_unreachable until an operator runs scripts/bootstrap-hosted-apps.sh). Everything below the "Python app hosting" heading describes the intended shape and is not yet a promise. For long-running FastAPI today, host it elsewhere (Fly / Render / a droplet) and call it from a Cloud custom function — see the FastAPI with LingCode Cloud tutorial.

This page is a factual reference for the two Python surfaces on LingCode Cloud: what runs, what sandboxes it, what the hard caps are, and where the line falls between them.

The two Python tiers

They exist because the trade-offs are genuinely different. One is optimized for cheap, safe, short bursts of code that trust nothing. The other is optimized for the "my whole app is Python" case where you want a real long-running process.

Why the sharp split

A per-invocation sandbox that can pip install arbitrary packages is very hard to make safe and very hard to make fast — every invocation would have to either warm a container or trust random C extensions. Instead the function tier is deliberately "stdlib only, but it starts in tens of milliseconds and is boxed off from the machine." The app-hosting tier accepts the container overhead in exchange for the full PyPI ecosystem and a real process lifecycle. You pick the one whose trade-offs you actually want.

Python custom functions

A Python function is a single file with a handler entry point:

def handler(input, ctx):
    row = ctx.db.query_read(
        "select id, title from posts where id = %s",
        [input["post_id"]],
    )
    return {"post": row[0] if row else None}

input is whatever JSON the caller sent. ctx exposes ctx.db and ctx.storage — both are synchronous wrappers over the same backend RPC endpoint (/_fn-rpc) that the Deno-TS runtime uses, so the wire contract is identical. Return value must be JSON-serializable; it's what the caller gets back.

Runtime shape

  • Interpreter: system python3, invoked as python3 -I -B -S -.
    • -I — isolated: ignores PYTHONPATH, PYTHONHOME, and user site.
    • -B — don't write .pyc files.
    • -S — don't run site.py.
  • STDIN: a JSON envelope { source, input, ctx }. STDOUT: an __LC_RESULT__ sentinel line followed by JSON {ok, data|error}. Same protocol as the Deno-TS runtime; observability tools see one contract.
  • Source, output, memory, process count, and wall clock are all capped (see the table above). If you exceed one you get an error result, not a silent kill.

Sandbox in one paragraph

Each invocation runs as its own firejail-wrapped process:

firejail --quiet --noprofile --private --net=none \
  --netfilter=/etc/lingcode/fn-gateway.nft \
  --caps.drop=all --seccomp --nonewprivs --nogroups --noroot \
  --rlimit-as=<memMb>MB --rlimit-cpu=<timeout+2s> --rlimit-nproc=32 \
  -- python3 -I -B -S -

Python has no in-interpreter "deny read this file" / "deny open this socket" primitive, so the guarantee comes from below the interpreter: a fresh mount namespace with a tmpfs $HOME and no writable filesystem beyond /usr, no network except a single --netfilter-punched hole for the backend gateway on port 443, no ambient capabilities, no setuid. If the container is compromised, there is nowhere useful to go. Setup is one-time via scripts/bootstrap-python-runtime.sh; you don't operate it.

Stdlib means stdlib. There is no pip install step and no shared virtualenv. If you need requests, use urllib.request. If you need pydantic, hand-roll the validation. If you actually need a third-party library, that is exactly the signal that you want the app-hosting tier for this piece of work, not a function.

The app-hosting tier accepts a full source tree — an app you'd normally deploy to a VPS — and turns it into a per-app Docker image running behind Caddy with automatic TLS. This is where FastAPI, Flask, Django, Starlette, or anything else in the Python web ecosystem lives.

What you upload

An extractable source tree with, at minimum, either a requirements.txt or a pyproject.toml at the top level. Without one of those, there's nothing for pip install to consume and the intake validator rejects the upload.

Everything else follows the ordinary Python conventions:

  • A FastAPI or ASGI app usually exposed as app in a module like main.py or app/main.py.
  • Optional Procfile with a web: line if you want to override the default entrypoint (uvicorn for ASGI, gunicorn for WSGI).
  • Static files, templates, whatever your framework expects — all shipped in-tree.

Hard caps at intake: 100 MB uncompressed total, 500 files, 5 MB per file. These exist to keep pip install's working set predictable and to cap the blast radius of a "million tiny files" extractor attack.

What the platform builds

A per-app Dockerfile on top of a pinned ghcr.io/lingcode/py-app-runtime:3.12 base image (only 3.12 is in SUPPORTED_RUNTIME_VERSIONS today). The build is layered to keep rebuilds fast:

FROM ghcr.io/lingcode/py-app-runtime:3.12
WORKDIR /app
COPY requirements.txt* ./
RUN if [ -f requirements.txt ]; then pip install --no-cache-dir -r requirements.txt; fi
COPY . .
ENV PORT=8080 HEALTHCHECK_PATH=/
EXPOSE 8080
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]

Requirements are copied and installed before the source is copied — that way editing your app doesn't invalidate the Python-dependency layer, and rebuilds after a source-only change are fast. The PORT and HEALTHCHECK_PATH environment variables are baked in with defaults but can be overridden at deploy time without a rebuild.

How requests get in

Each app gets an <app-id>.apps.lingcode.dev subdomain, served by Caddy with on-demand TLS — certificates are minted automatically the first time a hostname is hit. Custom domains work by pointing a CNAME at apps.lingcode.dev (or an A record at the edge IP) with proxying turned off in your DNS provider; the on-demand TLS handshake completes and the app is reachable. Same DNS story as for the Worker tier — see Connect a custom domain.

The container has one job: bind 0.0.0.0:$PORT and serve HTTP. Health is probed via GET $HEALTHCHECK_PATH; when that returns non-2xx for too long, the container is restarted.

Difference from the Worker tier

A hosted Worker app (see App hosting) is a V8 isolate — no filesystem, no child_process, no long-lived connections. A hosted Python app is a normal Linux process inside a container — it can hold a WebSocket open, run a background asyncio task, or open a file, because there is a real OS underneath. The tradeoff is start-up time and per-app footprint; hosted Python is heavier per instance than a Worker.

Everything else — same backend

Both tiers plug into the rest of the managed backend the same way:

  • Secrets live in the vault and are injected into function ctx or hosted-app environment. Never checked into your source tree.
  • Database access is the managed Postgres — for functions via ctx.db, for hosted apps via a normal psycopg / asyncpg / SQLAlchemy connection using the credentials in your environment.
  • Storage is the same object store; functions call ctx.storage, hosted apps use the REST endpoints or a client library.

The point is that your Python code doesn't have to change if you decide a piece of work is better served as a hosted app instead of a function (or vice versa) — the surrounding pieces stay put.

Which one should this be?

Two heuristics that tend to give the right answer once app hosting is live:

  • "Do I need PyPI?" If yes, it will be the hosted-app tier — for now, host elsewhere and call via a function. If no, functions handle it today.
  • "Does anything about this call have to keep running — a WebSocket, a job queue worker, a background task, an in-memory cache — after the request that started it returns?" If yes, it will be the hosted-app tier — for now, host elsewhere. Functions are per-invocation processes.

Everything else is a genuinely local call, and the smaller, sandboxed function surface is the right default today.
