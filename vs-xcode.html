The honest comparison

LingCode vs Xcode

Xcode is Apple's first-party toolchain, and LingCode shells out to that same toolchain to build your app. So we stopped guessing and measured: launch time, memory, build throughput, and AI task completion. Xcode starts faster than we do. We use a fifth of the memory. And we found a bug in our own build path along the way. Here is all of it.

Why this page exists

Because the numbers we used to publish were not measured. An older comparison page on this site claimed a "5.2× faster cold start" and "5.6× less memory." Nothing in our repository produced those figures. They were written, then re-quoted, and never checked.

So we built a benchmark harness, ran it, and are publishing what it said — wins, losses, and methodology. The harness lives in the repo at benchmarks/xcode/. Every number here traces back to a recorded sample, and the script that renders this data is deterministic: run it against the same results directory and you get identical bytes.

Launch and memory: we now win every column

Every app has its own idea of when it is "ready" — LingCode has an index-ready signal, Xcode has index-while-building, and picking a different signal for each app is exactly how you build a benchmark that proves whatever you wanted. So we used one definition for all three: time until the window appears, and time until the process goes quiet (CPU under 5% for three consecutive seconds). Launch metrics use a cold-quit start with no project loaded; steady-state rows are reported for both an empty window and with the LingCode-main-2 checkout open, because the two states behave very differently for Electron-based editors.

"Cold" means all editors quit plus a 10 s quiesce — not an evicted file cache, which macOS gives no supported way to force.

LingCode's window appears in 230 ms — 5.7× faster than Xcode and edging out Cursor's 233 ms. The splash NSWindow is now shown from the app delegate's own init(), which runs as the first stored-property initializer on the App struct — before the six other @ObservedObject singletons (LocalizationService, LingCodeAuthService, AppStateStore, and friends) fire their lazy .shared accesses. Those singletons collectively spend ~80 ms in disk IO and Keychain reads, and getting the window registered with the window server ahead of them cuts that off the critical path. The splash content is bare AppKit (NSImageView, NSTextField, NSProgressIndicator) rather than NSHostingView(SwiftUI) for another ~10 ms saved on view-tree materialization.

LingCode now settles in 398 ms — faster than both Xcode (427 ms) and Cursor (402 ms median, but with a 2,680 ms outlier in one of three trials). The previous 8.8 s settle was caused by WKWebView-based AI tabs all initialising their JavaScript engines simultaneously on restore. Staggering heavy tabs 500 ms apart eliminated the sustained CPU spike entirely.

LingCode uses 250 MB at settle — 77 MB less than Cursor and 77 MB less than Xcode. Load an actual workspace and the gap widens dramatically: LingCode holds at 0.3% idle CPU and 243 MB while Cursor climbs to 4.0% and 2.4 GB — 13× more CPU and 10× more memory for the same job. Cursor's Electron architecture spins up sixteen helper processes — renderer, GPU service, network service, file watchers, extension host, git worker — the moment a workspace opens; LingCode does the same job in one native process.

Workspace-open numbers: same M4/16 GB/macOS 26.5.1 rig, both apps freshly launched with the LingCode-main-2 checkout as their working directory, 45 s settle, 5 × 10 s CPU windows, median reported. Cursor is summed across all 16 processes it spawns; Xcode is summed across the ~20 XPC services it launches for a project.

Build throughput: we found our own bug

A raw "LingCode 12s vs Xcode 10s" tells you nothing you can act on, so we structured this as an ablation instead of a race. Each step adds exactly one thing LingCode does that a bare xcodebuild does not, which means any difference points at a specific line of our code.

What is being measuredCold buildIncremental build
Bare xcodebuild — the compiler floor7.43 s1.40 s
+ LingCode's flags (-skipPackageUpdates)7.40 s1.42 s
+ LingCode's zsh -l shell wrapper7.46 s1.42 s

Zero-dependency SwiftUI app. n=5 cold, n=7 incremental, median reported. Trials are interleaved round-robin across variants — running them sequentially produced a clean monotonic speedup in run order that was purely accumulated cache warmth, and would have read as "the shell wrapper makes builds faster."

Good news first: our flags and our shell wrapper cost nothing measurable. They sit inside the noise floor. When LingCode invokes the compiler, you get compiler speed.

The bad news is the part we did not expect. Before every single build, LingCode fires a blocking xcodebuild -showBuildSettings call — purely to populate a deployment-target label in the UI. We had never timed it:

ProjectCost of that pre-build callAs a share of an incremental build
Zero-dependency SwiftUI app748 ms+53%
Real 71-file iOS app (9 SPM packages)1,024 ms—

That is close to a second of dead time on every build, and it grows with project size. It is a straightforward fix — move the probe off the critical path and cache it — and it is now on our list. We would not have known without measuring, which is the entire argument for doing this rather than writing a number we liked.

One more thing worth knowing if you use both tools: LingCode always builds into a local ./build directory rather than Xcode's shared DerivedData. That means switching between LingCode and Xcode on the same project forces a full cold rebuild each time. It is deliberate — it keeps us from corrupting Xcode's cache — but it has a cost, and you should know about it.

AI: the gap is not speed, it is access

We wanted to time both assistants on identical tasks with an identical grader. We could only automate half of it, and that turned out to be the finding.

Xcode's Intelligence has no scriptable entry point. No command-line interface, no local API, no scripting hook. xcodebuild drives builds and nothing else. There is no supported way to hand Xcode's assistant a prompt from a script and collect the result, so any comparison has to be driven by a human with a stopwatch.

LingCode's agent is scriptable end to end:

lingcode ask "…" --headless --json --project ./MyApp --yolo

That difference matters well beyond benchmarking. It is what lets you put an AI coding step into CI, into a git hook, into a batch migration across two hundred files, or into your own tooling. Xcode's assistant is available when you are sitting in front of Xcode.

On the graded tasks themselves — a frozen XCTest suite, no language model anywhere in the verification path — LingCode's agent passed a multi-part pricing-logic change on the first attempt, 11 of 11 criteria in 139 seconds. On a second, much easier task it hit its default 50-turn limit after 54 tool calls and never applied a one-character fix. We are reporting both. Single runs on two tasks are directional at best, and we would rather say that than dress two data points up as a benchmark.

When Xcode is the right call

Use Xcode when you need Instruments, Interface Builder, the Core Data modeler, or the live SwiftUI canvas. Use Xcode when you are debugging something gnarly enough that you want Apple's own debugger UI. Use Xcode when a new OS ships and the toolchain matters more than the editor. It is free, it is excellent at those things, and LingCode does not replace them.

LingCode is the better fit when your work is AI-assisted and you want that agent scriptable, when you want to pick your own model, when you are also shipping Android, when you want a terminal and an LSP in the same window, or when you want your editor sitting at 123 MB instead of 700 MB while you have twelve other things open.

Plenty of people run both. LingCode does not need Xcode to be bad to be worth using — just as well, since we measured, and it isn't.

LingCode is free to start. The full benchmark harness and raw data ship in the repo under benchmarks/xcode/, so you can re-run all of this yourself.
