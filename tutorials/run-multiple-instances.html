Run multiple instances at once

macOS normally runs one copy of an app. Sometimes you want two — one LingCode to build the IDE itself while another runs your real project, or two copies of the app you're developing to test multi-window behaviour. Here's how, for both cases.

The one idea behind all of this

0

Click an app's icon a second time and macOS doesn't start a new copy — it just brings the running window forward. That's the default, and it's usually what you want. But two situations make a second copy genuinely useful:

  • One IDE to build the IDE, another to use it. Keep a stable LingCode open for real work while a second LingCode edits and rebuilds LingCode's own source.
  • Two heavy projects at once. Run a long agent task or a big build in one window without it competing with another project for the same window's state.
  • Test your own app's multi-window behaviour. A chat app, a game lobby, a collaborative editor — you often need two copies talking to each other to test them.

The mechanism is the same in every case, and it has two halves:

  1. Tell macOS to force a new process — that's the open -n flag.
  2. Make sure the app doesn't block itself. Many apps notice a running copy of themselves and quit the newcomer (a "single-instance guard"). If one exists, you have to opt out of it.

Parts 1 and 2 below are just those two halves applied to the IDE and to your own app.

Part 1 — Multiple LingCode IDE instances

1

LingCode ships with a single-instance guard on purpose (it stops a notification or a "reopen" from spawning a stray second window). You opt out of it with a small marker file. Create it once:

touch ~/.lingcode-allow-multiple-instances

While that file exists, LingCode skips the guard. Delete it to go back to normal single-instance behaviour:

rm ~/.lingcode-allow-multiple-instances
Why a file, not a settings toggle? It's unambiguous and scriptable — there's no dependence on which preferences store the app happens to read, which is exactly the kind of subtlety that makes "I set the flag but nothing changed" bugs.

Launch the extra instances

2

A normal double-click still just focuses the existing window. To force a new instance, use open -n (the -n means "open a new instance"):

open -n /Applications/LingCode.app

Run it again for a third, a fourth, and so on. Each is a full, independent IDE.

Typing a command every time gets old. Two quick shortcuts:

  • A shell alias — add to ~/.zshrc: 
    alias lingcode-new='open -n /Applications/LingCode.app'
    Then just run lingcode-new.
  • A double-clickable launcher — in Automator, make an Application with one "Run Shell Script" step containing open -n /Applications/LingCode.app, and save it as "New LingCode". Now it lives in your Dock like any app.

Know the trade-off

3

Every LingCode instance shares the same identity (hainanmandi.LingCode), so they share one settings store and one Keychain (API keys, sign-in).

In practice: open different projects in each instance freely, but don't change global Settings in two instances at the same moment — the last writer wins and can quietly overwrite the other. This is a convenience, not isolation.

Need true isolation? If you want separate settings and separate keys per copy, that takes a separate build with its own bundle identifier — a "LingCode Dev" channel, the way Chrome ships alongside Chrome Canary. Multi-instance and a separate channel are different tools; pick the one that fits.

Part 2 — Multiple instances of the app you're building

4

This is about your app — the one you Build & Run from inside LingCode — not the IDE. Same rule applies: macOS can run several copies, but your app might block it. Two cases.

Case A — your app does not enforce single-instance (most apps). Then it's purely a launch question. Build in LingCode as usual, then launch extra copies of the build product with open -n:

open -n /path/to/YourApp.app

Finding the product: after a successful build the .app lands in your build output — for Xcode-style projects that's ~/Library/Developer/Xcode/DerivedData/<YourProject>-…/Build/Products/Debug/YourApp.app. Reveal it in Finder, then type open -n in Terminal and drag the app onto the window to fill in the path.

Tip: LingCode's Run action launches the first copy for you. To get more running alongside it, point open -n at the same build product — the first came from Run, each open -n adds another.

If your app blocks its own second copy

5

Case B — if open -n makes a second copy flash on screen and immediately quit, your app is detecting itself and bowing out, exactly like LingCode's guard. Find that code and gate it behind an opt-out. In Swift/AppKit it usually looks like this early in launch:

let others = NSRunningApplication
    .runningApplications(withBundleIdentifier: Bundle.main.bundleIdentifier!)
    .filter { $0.processIdentifier != NSRunningApplication.current.processIdentifier }
if !others.isEmpty {
    // ... activate the existing one and exit(0) ...
}

Wrap it so it can be skipped — the same marker-file trick works cleanly:

let allowMultiple = FileManager.default.fileExists(
    atPath: NSHomeDirectory() + "/.yourapp-allow-multiple-instances")
if !allowMultiple {
    // ... existing single-instance guard ...
}

Then touch ~/.yourapp-allow-multiple-instances, rebuild, and open -n works. For frameworks with a built-in lock — Electron's app.requestSingleInstanceLock(), Qt's QtSingleApplication, a Tauri single-instance plugin — make that lock conditional instead of unconditional.

Sharing data between copies

6

Just like the IDE, two copies of your app share one settings store and Keychain by default (same bundle id). If your app also writes to a single SQLite file or binds a fixed port, two instances will collide on those too.

When you genuinely need them isolated, give each its own data directory — pass a --data-dir argument, or key your storage off an instance id you generate at launch. Then two copies can run without stepping on each other's state.

Troubleshooting

7
  • open -n just focuses the existing window, no new copy. The single-instance guard is still active. For LingCode, confirm ~/.lingcode-allow-multiple-instances exists. For your app, see Part 2 Case B.
  • Second copy appears for a split second, then quits. Same cause — the guard ran and called exit(). Gate it behind the marker file.
  • Settings or API keys keep resetting. Two instances both wrote global preferences. Avoid changing global Settings in more than one instance at once, or move to a separate-identity build for real isolation.
  • "App is damaged / can't be opened" on a hand-built copy. It isn't signed/notarized for distribution. On your own machine that's fine — right-click → Open once to clear Gatekeeper, or build with your developer signing identity.

Quick reference

8
# LingCode IDE — enable, launch, disable
touch ~/.lingcode-allow-multiple-instances
open -n /Applications/LingCode.app          # repeat for more
rm ~/.lingcode-allow-multiple-instances

# Any app you built (no self-guard)
open -n /path/to/YourApp.app                # repeat for more
