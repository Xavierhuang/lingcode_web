Tutorials / Backend integrations / Use FastAPI with LingCode Cloud
📝 Written ● Intermediate Updated 2026-08-13

Can I run FastAPI on LingCode Cloud?

TL;DR: No — LingCode Cloud custom functions are short-lived per-invocation subprocesses (Deno-TS or, in Preview, stdlib-only Python), not long-running HTTP servers. Host your FastAPI app somewhere that does run long-lived processes (Fly, Render, Railway, a droplet), keep its URL and any auth token in your backend's Secrets vault, and call it from a Cloud custom function via the http-fetch template. Your frontend never sees the token; your FastAPI service stays private.

FastAPI is a long-running ASGI framework — you uvicorn app:app, it binds a port, and it lives for hours serving requests. LingCode Cloud custom functions run in the opposite model: a fresh sandbox spawns per call, executes one handler, prints a result, exits. Neither the Deno-TS runtime nor the Preview Python runtime can host an ASGI server, and neither installs PyPI packages (the Preview is deliberately stdlib-only). That's not a shortcoming to work around — it's a different job. This tutorial covers the pattern that does fit: FastAPI hosted elsewhere, safely proxied through your Cloud backend.

This builds on a connected managed backend and assumes you already have (or can deploy) a FastAPI app somewhere reachable over HTTPS.

What you'll learn

  • Why FastAPI can't run inside a LingCode Cloud custom function
  • How to keep your FastAPI service private and only reachable through the Cloud backend
  • The http-fetch one-liner your frontend calls, and how the Secrets vault swaps in the auth token
  • When to skip the proxy entirely (public FastAPI + no server-side secret)

Step 1 — deploy FastAPI wherever long-running processes live

Any host that supervises a Python process will do. Fly, Render, Railway, a DigitalOcean droplet, an AWS Lightsail instance — the common shape is: a Docker image or a Nix/buildpack that runs uvicorn app:app --host 0.0.0.0 --port $PORT. Keep this bit boring; the point of the pattern below is that where FastAPI runs stops mattering to your app once the Cloud backend fronts it.

Give your service one hardening rule at deploy time: require a shared secret in every request. A single header like X-Backend-Token checked at the top of every route is enough. This means only callers who know the token can invoke your API — and in the Cloud pattern, only the backend knows it. Sample:

from fastapi import FastAPI, Header, HTTPException
import os

app = FastAPI()
BACKEND_TOKEN = os.environ["BACKEND_TOKEN"]  # set in Fly/Render env

@app.post("/score")
def score(payload: dict, x_backend_token: str = Header(...)):
    if x_backend_token != BACKEND_TOKEN:
        raise HTTPException(status_code=401, detail="unauthorized")
    # ... do the actual work
    return {"score": 0.87}

Step 2 — store the token as a Cloud secret

Open lingcode.dev/backends, pick your backend, go to Settings → Secrets & integrations, and add:

  • FASTAPI_URL = https://your-fastapi.fly.dev (the base URL of your deployed app)
  • FASTAPI_TOKEN = the same value you set as BACKEND_TOKEN above

Both are encrypted at rest (AES-256-GCM) and only readable by backend functions — never by your frontend. The console shows the names afterward, never the values.

Step 3 — allow-list the host, then call it via http-fetch

Under Settings → Allowed fetch hosts, add your FastAPI host (e.g. your-fastapi.fly.dev). The http-fetch function template is deliberately blocked from every host that isn't on this list — see the note below on why.

From your app, one call:

const { data, error } = await client.functions.invoke('http-fetch', {
  url: '{{FASTAPI_URL}}/score',
  method: 'POST',
  headers: {
    'X-Backend-Token': '{{FASTAPI_TOKEN}}',
    'content-type': 'application/json',
  },
  body: { text: 'the thing to score' },
});
if (error) { console.error(error.message); return; }
console.log(data.body.score);   // -> 0.87

The {{FASTAPI_URL}} and {{FASTAPI_TOKEN}} tokens are replaced server-side with the secret values before the outbound request is made — the request your app makes to LingCode contains no secrets at all. data carries status, headers, and body (parsed as JSON when the upstream Content-Type says so).

Why the allow-list?

http-fetch runs inside LingCode's network, so an unrestricted "fetch any URL" would be a server-side request forgery (SSRF) hole — a way to probe internal services. The allow-list is the guard: only domains you explicitly add are reachable, and requests are additionally blocked from resolving to any private/internal address. An empty allow-list means no outbound calls at all. Add exactly the FastAPI host, nothing broader.

Why not just have my frontend call FastAPI directly?

You can — if the FastAPI endpoint is genuinely public and needs no secret. But the moment you have anything the caller shouldn't hold (an API key, a paid-service token, a rate-limit-scoped credential, database access), you need a server-side hop. The Cloud backend is that hop, without you having to stand one up. And keeping FastAPI behind a required X-Backend-Token means even someone who guesses the URL can't invoke it.

When the answer really is "run FastAPI on LingCode Cloud"

Today it isn't. The custom-functions runtime deliberately does not host long-lived processes — that's the domain of app hosting, which currently supports Node/Worker apps. First-class Python app hosting (a supervised uvicorn process per project, with venv + healthchecks + logs) is a separate project on the roadmap, not something the Preview Python runtime is going to grow into. If you need it before we ship it, the pattern above is what production LingCode Cloud users use.

Do not paste live tokens into your frontend, a prompt, or an environment that ships to the browser. The whole shape of this pattern is that FASTAPI_TOKEN lives only in the Cloud vault and only http-fetch ever sees it. If a token leaks, rotate it in your FastAPI env AND update the Cloud secret — the two must match.
